# 同类工具对照与时间森林定位

核对日期：2026-09-07。对照官方仓库/文档，并阅读时间森林的实际实现；未安装、运行或对同类工具做画质、速度、显存测试。下文区分公开说明、代码事实与产品定位判断。文档未提到某功能不等于该工具没有，不用猜测填写“×”。

## 为什么上一版介绍不够准确

上一版主要参考README结构，强调队列、图库、种子、回收站和图片编辑。这些可以说明使用便利，但不足以解释时间森林为何值得选择；同时漏掉视频内部任务规划、已选结果的上下文依赖、返工影响范围、原8＋4生成链和角色图声绑定。Stability Matrix以环境/包管理为主，适合参考介绍结构，不适合作为主要功能竞品。

## 横向比较

| 工具及一手来源 | 已明确提供的相关能力 | 对时间森林定位的影响 |
|---|---|---|
| [ComfyUI](https://github.com/Comfy-Org/ComfyUI#features) | 节点图、可复用工作流/API、多种生成模态、队列与内存管理；App Mode也可把工作流呈现为简化界面。 | “为ComfyUI做一个简单界面”不够。时间森林的重点应是已适配工作流之上的项目、分镜、审核、依赖与资产组织；通用图编辑/模型覆盖不是我们的优势。 |
| [SwarmUI](https://github.com/mcmonkeyprojects/SwarmUI) | Generate界面与Comfy Workflow图界面并存，图像编辑、参数网格、多种图像/视频模型，包括H3；[提示词语法](https://github.com/mcmonkeyprojects/SwarmUI/blob/master/docs/Features/Prompt%20Syntax.md)另有视频扩展。 | 易用参数页、模型选择和视频生成已很常见。时间森林应展示一个镜头反复制作后如何选用、影响后续并进入成片，而非只展示参数按钮。 |
| [Wan2GP / WanGP](https://github.com/deepbeepmeep/Wan2GP) | 多模型、量化/低显存、队列、媒体图库/复用；H3已经支持多帧运动及匹配音频续接，滑窗可指定各段时长/提示词/新镜头。 | 是直接对照对象。不能声称我们独有长视频、声画续接、人物驱动或低显存。时间森林可突出固定项目结构、镜头候选审核和资产版本引用；尚无依据宣称比它更快、省显存或一致性更好。 |
| [ComfyUI MiniMax H3 Director（上游）](https://github.com/seesee75-commits/ComfyUI-MiniMaxH3-Director) | H3时间线、图/视频/声音参考、提示词编译与实时预览、Retake。当前README明确其Director Chain已撤回，长时间线分窗链尚未解决，直接运行更长窗口是另一回事。 | 同模型的直接对照。时间森林已经有单独的分镜/内部任务规划和接续保存，但不能据此声称界面编辑能力全面更强。不要用仍介绍Chain的旧fork代替上游现状。 |
| [LTX Director](https://github.com/WhatDreamsCost/WhatDreamsCost-ComfyUI) | 时间线裁切、分割、组合和扩展视频，IC-LoRA、声音补绘、Retake Beta，以及时间线保存/加载。 | “导演”“分镜”“重拍”都不是独有。时间森林当前强项在制作项目的选用与依赖管理；没有依据宣称已具备同等自由时间线剪辑、任意时间范围重拍或音频补绘。 |
| [InvokeAI](https://github.com/invoke-ai/InvokeAI)及[Gallery文档](https://invoke.ai/features/gallery/) | 统一画布、工作流编辑和图库；当前图库同时容纳图片与视频，支持Boards组织及结果复用。 | 不能把它描述成只有单图生成。时间森林应讲清图片候选如何进入视频角色/声音素材、固定版本和生成来源记录，而非仅强调“有资产库”。 |

这是功能组织方式的比较，不是排行榜。时间森林优势的判断来自自身已实现机制与目标使用场景，没有证明竞争产品缺少等价扩展。

## 回到代码：值得放进介绍的五个重点

| 重点 | 已核对的具体实现 | 用户价值与表述边界 |
|---|---|---|
| 创作分镜与内部渲染分开 | `studio_story.py:storyboard/task_segments`按每≤15秒的用户分镜组织正文，内部规划合法帧数、上下文、交付长度；自然/精确时长有不同规划。 | 用户不必为每个底层任务另写提示词。精确模式通过规划/裁切处理时长，不把音视频拉伸当补足；不保证台词事件精确按秒执行。 |
| 返工考虑后续依赖 | `studio.py:previous/approve/reroll/edit_plan`要求连续段使用前段已选结果；换候选或改条件使相关后续选用失效，在新场景处停止连续级联；`studio_story.py:continue_story`核对原快照后接续未完成任务。 | 例：P2改选候选，依赖它的P3/P4不能继续冒充当前成片；旧候选文件仍保留。不是非破坏时间线编辑的替代，也不自动重跑整部作品。 |
| 有具体执行依据的声画长链 | `studio_tail.py:save_tail/validate_tail`为dance_split保存二采交付尾部22帧无损图像和对齐声音，校验来源/模型/VAE/尺寸；`studio_recipes.py:compile`编码为后段上下文。其他配方按各自AV检查点处理。 | 后段连接实际选用版本；减少把压缩预览或未交付未来帧作为上下文的风险。多帧声画续接不是独有能力，无损检查点不等于画面永不漂移。 |
| 原8＋4及官方备选进入同一制作流程 | `studio_recipes.py:RECIPES/defaults/compile`保留12步日程8＋4切分、学习型潜空间放大和二采声画输出，另有官方Ref2VA/T2VA、文戏适配；能力目录按配方提供低显存分块/Sage等项。 | 适用模式可选择不同已适配核心，继续共用编排、审核和资产流程。讲清真实路径而非泛称“优化”；不宣称通吃模型、16GB全功能保证或实测速度领先。 |
| 角色、素材版本与生成来源连起来 | `swap_template_v3.py`把目标脸/发型/体型/服装与源视频表演分工；`studio_prompts.py`按subject关联图像与声音；`asset_library/bindings.py/project_import.py/results.py`固定版本导入并登记确切候选/成片来源。 | 可围绕角色反复制作，图声各有用途，换资产版本不会暗改旧项目。整体人物重塑是请求目标和工作流能力，不是每次成功的质量保证；同类工具也有角色/声音参考。 |

源码均相对仓库根目录，其中studio_*、swap_template_v3.py位于h3ui/。字段/节点细节以[参数映射](../frontend/parameter-map.md)为唯一维护来源，不在本文另建能力表。

## 视觉设计与交互体验也是核心价值

用户明确把UI和交互体验列为核心优势。此前对照偏重技术能力，把队列、计时和筛选降为辅助，未充分说明这些操作在一个协调界面中如何共同服务创作。单个能力常见，不意味着其组织方式和整体体验没有价值。

本项目的依据是现有工作区与公共组件：纸色/森林绿配色、衬线标题、媒体主体与辅助信息层级；按制作步骤组织任务；四模式共用制作参数外壳、状态计时、错误和候选整理。图片的重复生成、返回上一步、恢复默认与快捷入库，让反复尝试可以在原创作过程中完成。实现入口见static/studio/ui/及styles/workbench.css，交互语义见[公共交互契约](../frontend/parameter-and-interaction-contract.md)。

这是设计特征和用户价值的说明。本轮没有进行同类界面的受控可用性实验或审美评测，不能据此宣称其他导演台都不好看、时间森林最好看或操作效率领先。正式介绍以自身设计和具体操作为证据，横向资料仍用于校准能力范围。

## 应当怎样定位

**注重视觉设计与交互体验的本地AI导演工作台。在统一的界面中组织图片创作、角色替换、长视频分镜、声画生成和资产管理，让一部作品能够持续制作、筛选和返工。**

这是综合产品定位，不是“独家功能”的断言。适合反复调整角色、表演、对白和镜头衔接，并希望保留不同结果来路的创作者。若用户首要需求是广泛模型覆盖、快速试新模型、任意节点图或成熟时间线剪辑，同类工具有各自更明确的侧重。

正式介绍顺序为视觉与交互体验、四模式、反复生成与筛选、长项目编排和返工、资产复用、工作流与使用条件。队列/计时/回收站是连贯体验的具体例子；内部渲染和声画接续作为能力支撑，避免开篇淹没产品价值。当前真实生成验证范围仍读[维护基线](../maintenance-baseline.md)，不能用文案修订或本次桌面研究替代性能与用户验收。
