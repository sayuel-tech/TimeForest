# 正式 H3 Prompt 模板

> V2.9：本文件为可读设计说明。未来运行读取 `运行模板/` 的对应纯TXT，任务/Schema/正文取值以 `配套清单/llm-task-registry.json` 为准；原“字段未定”说明不覆盖新合同。未进行模型实测。

**任务：h3_prompt｜剧本模式第五页｜当前示例选择完整文案路线**

## 1. 网站应提供什么

确认的分镜和片段、精确保留的对白、有效人物与素材用途、网站分配的媒体标签和主体映射、预期起止状态、续接意图、当前工作流能力，以及本次使用完整文案还是结构化字段组装。

正式指导内容来自实际采用的工作流表达约定，不因模型名字叫 H3 就假定所有路线输入相同。上游视频还没有生成时，只提供明确的未来来源约定和预期状态，不提供伪造 Take。

## 2. 给模型的任务草案

```text
根据已经确认的当前片段，为所给 H3 工作流创作正式候选 Prompt。你的任务是把已确定内容表达得更适合生成，不是重新写剧情。

按动作和视听节奏清楚表达本段的开端、变化与结束。保持用户确定的人物、服装、空间、对白和声音安排。台词不得擅自润色、换人或补写下一段内容。

只使用网站分配的素材标签与主体映射，不重新编号 Picture、Audio 或其他输入，不凭资产在资料列表中的位置猜标签。某参考仅用于氛围、构图或声音时，按其用途描述，不把它变成全部内容来源。

区分预期上游状态与已提供的真实参考观察。未来尾部来源可以按约定使用，但不能写成你已经看过尚未生成的视频。

使用本次明确选择的文案组装方式。完整文案路线交付完整 prompt_text，包含指导要求的必要结构；结构化路线只返回指定字段，不额外包一整份模板。

不要发明节点、模型文件、采样参数、帧数规则或未接入的硬控制。轨迹仅为文字意图时，不声称工作流会精确执行路径。

payload 只放本次正式候选与使用的引用。不要附“以下是提示词”、使用教程、模型优缺点、多个未请求版本或创作解析。必要问题放外层。
```

## 3. 当前示例 payload

`prompt_text` 与 `used_reference_keys`。这里的“完整”表示与所选执行契约一致的完整模型文案，不表示只要有一个长字符串就必然能直接进入任意工作流。

V2.7 明确：本样例仅对应网站已经选择完整文案路径的请求。选择结构化路径时，由网站提供另一份与现有适配一致的字段契约，不能让模型在同一请求自由二选一，也不同时返回可各自编辑的 prompt_text 和结构化正文。机器契约仍是设计草案，不在这里猜造具体 recipe 的现有字段。

`used_reference_keys` 用来检查本次采用的引用，不包含未实际传入的私有文件路径。引用合法性和标签匹配由网站校验，模型自己报告的列表不能代替核查正文。

## 4. 不要重复包裹

实际代码 `h3ui/studio_prompts.py` 存在完整与结构化路径；结构化路径可能加入主体定义、summary、detailed_description、声音和时长规则。[R06，见主目录文档 10]

因此，在完整文案候选外面再自动加一套同类模板，可能造成重复。第五页建议展示最终文案预览与适用模式，让确认内容与实际输入一致。具体选择归入 Q06。

某些英文结构标题是 H3 文案的一部分，不是多余聊天内容，不能统一删除。应剥离的是通讯外层和面向用户的解释，而不是模型确实需要的格式。

## 5. 生成接续的动态部分

剧本阶段可以确认“承接片段 A 的指定采用结果尾部”这一输入契约。电影第一页在准备请求时落实具体媒体与取用范围，并固定在执行记录中。

若落实后的素材形式、标签或关键状态不适用，应提示复核。不能为了勉强运行让电影侧 LLM 自动改下一段剧情。成片第二页后来的裁切也不改写这份历史输入。

## 6. 继续打磨

完整模式与结构化模式的工作流对应、动态时序预览、局部人工调整如何显示差异，是重点。此模板不预设某种写法已经在用户设备上生成更好。
