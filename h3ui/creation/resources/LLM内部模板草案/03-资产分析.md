# 资产分析模板

> V2.9：本文件为可读设计说明。未来运行读取 `运行模板/` 的对应纯TXT，任务/Schema/正文取值以 `配套清单/llm-task-registry.json` 为准；原“字段未定”说明不覆盖新合同。未进行模型实测。

**任务：asset_analysis｜剧本模式第三页**

## 输入

确认的本次剧本范围、已有需求与绑定、用户主动提供的资产候选清单，以及允许纳入分析的角色、场景、声音、风格等资料。

## 给模型的任务草案

```text
识别当前剧本中值得准备或重复使用的资产需求。关注有助于人物身份、场景、重要道具、服装、声音和视觉风格一致性的内容，不把所有出现的名词都变成强制资产。

对每项需求写清它是什么、依据哪段内容、用途是什么，以及可以怎样准备。区别“故事需要它”与“当前工作流必须有一个媒体文件”。未准备媒体不自动意味着剧情不成立。

只在网站提供的资产候选清单里提出匹配建议。没有提供完整资产库时，不声称已经搜索全库；不虚构 ID，不自动绑定，不把名称相近当成同一人物。

保留用户已经明确接受的文字设定与绑定决定。需要调整时说明相关冲突，不把用户决定默默改回你的初始建议。

仅返回需求和建议。不要附长篇资产管理教程，不生成图片或声音，也不宣布入库成功。
```

## 建议 payload

`needs` 有序列表。每项可包含临时或既有 `ref`、`kind`、`name`、`description`、`source_refs`、`media_need` 与 `suggested_asset_refs`。

`media_need` 可以表达文字即可、建议媒体、依据当前能力确认需要媒体或尚待确认。它不是让 LLM 发明生成阻塞规则；真正的必需输入由工作流预检决定。

## 呈现与应用

网站将需求呈现为可阅读卡片；用户可以绑定已有资产、保留文字、暂时留空或明确不采用。模型的匹配建议不直接改变绑定。

原有需求被重命名时按身份对照，避免同一个人物被新增成第二张卡。应用分析候选与确认资产绑定仍是两个动作。

## 继续打磨

需求怎样合并、重复角色怎样提示、可选资产是否默认折叠属于交互问题。当前不新增自动全库语义搜索服务。
